# 律师使用手册

适用对象：移民律师、律所管理员、案件助理和文案人员。  
适用版本：当前系统实现版。

本平台用于辅助移民案件材料整理、事实提取、翻译、知识库管理、任务跟进、文案生成和 AI 重写。平台可以提高整理效率，但不能替代律师的事实核验、法律判断和最终审核。

## 1. 5 分钟快速上手

如果是第一次使用，建议按下面顺序完成一个小案件测试：

1. 注册或登录账号。
2. 进入「设置」→「个人信息」，确认姓名、联系电话和所属律所。
3. 进入「设置」→「模型设置」，确认当前大模型配置，并点击「测试生成」。
4. 进入「案件管理」，新建一个测试案件。
5. 进入案件详情页，打开「文件管理」，上传 1-2 份清晰材料。
6. 对上传文件点击「AI 解析」，必要时输入提示词。
7. 进入「事实库」，审核、编辑并确认系统提取的事实。
8. 进入「文案工作台」，选择已确认事实，输入生成要求，生成草稿。
9. 对生成文案进行人工审核、AI 重写或翻译。
10. 在「任务中心」记录需要客户补充或律师复核的事项。

推荐先用一个非紧急案件试运行，熟悉流程后再用于正式案件。

## 2. 推荐案件工作流

建议把每个案件按这个顺序推进：

```text
创建案件
→ 上传文件
→ AI 解析文件
→ 审核事实
→ 确认可用事实
→ 补充知识库参考
→ 生成文案
→ 律师审核和重写
→ 创建补材料任务
→ 更新事实和文案
→ 定稿
```

核心原则：

- 先整理证据，再生成文案。
- 先确认事实，再用于正式草稿。
- AI 输出只作为初稿，最终内容必须由律师审核。

## 3. 登录与个人设置

1. 打开系统地址，使用邮箱和密码登录。
2. 首次注册时必须填写律所或公司名称，系统会自动创建组织。
3. 进入「设置」→「个人信息」，维护姓名、联系电话，并查看所属公司/律所。
4. 进入「设置」→「外观」，可选择「明亮版」或「经典暗色版」。
5. 进入「设置」→「安全」，可修改登录密码。注册和修改密码时都需要输入两次一致的密码。

建议律所内部统一账号命名、权限管理和离职账号处理流程。

## 4. 模型设置

进入「设置」→「模型设置」，可以查看和配置平台调用的大模型。

需要关注四个字段：

- Provider：供应商或网关名称，例如 `minimax`、`openai`、`claude`、`gemini`、`ollama` 或自定义。
- Model：实际模型名称，例如供应商文档中要求填写的模型 ID。
- Base URL：OpenAI-compatible `/v1` 地址。
- API Key：供应商密钥。

页面显示的是程序实际使用的生效配置。配置优先级为：

```text
网页中保存的组织配置 > 后端环境变量 > 程序默认值
```

API Key 不会明文回显。页面只会提示：

- 已保存组织 API Key：说明 Key 存在数据库组织设置里。
- 正在使用系统环境 API Key：说明 Key 来自服务器或 Railway 环境变量。
- 未配置 API Key：说明当前没有可用 Key。

修改 Provider、Model、Base URL 或 API Key 后，必须先保存，再点击「测试生成」。如果使用 Docker 或 Railway 修改环境变量，服务需要重启或 Redeploy 后才会生效。

## 5. 创建和维护案件

1. 进入「案件管理」，点击「新建案件」。
2. 填写案件标题、案件类型、客户姓名、客户邮箱或客户电话。
3. 客户邮箱和电话至少填写一个，便于后续补材料沟通。
4. 律师可在案件编辑弹窗或案件详情页修改案件状态：
   接案、事实提取、文案起草、律师审核、已递交。
5. 案件详情页会展示案件类型、客户姓名、客户邮箱、客户电话和当前状态。

建议案件名称使用统一格式，例如：

```text
客户姓名 - EB-1A
客户姓名 - NIW
客户姓名 - I-485
```

## 6. 上传和解析文档

进入某个案件后，打开「文件管理」。

1. 选择文件类型，例如证据材料、获奖证明、专利、论文、引用数据、雇佣证明、媒体报道、推荐信等。
2. 拖拽或点击上传文件。
3. 上传后不会自动解析，律师需要点击「AI 解析」。
4. 解析弹窗可输入律师提示词，也可从知识库检索并载入提示词模板。
5. 文档列表提供两个下载动作：
   「原始文件」下载上传原件；「解析文案」导出当前文档已提取的全部事实。

文件解析成功不代表内容完全准确。律师应重点检查：

- 姓名、日期、机构名称是否正确。
- 扫描件 OCR 是否有错字。
- 表格、印章、页眉页脚是否被误读。
- 中文、英文混合内容是否被拆错。
- 关键证据是否完整保留。

提示词示例：

```text
请从这份材料中提取可用于 EB-1A original contributions 的事实。
重点关注客户的具体贡献、采用情况、第三方评价和可量化影响。
不要补充文件中不存在的信息。
```

## 7. 事实库审核

进入「事实库」查看系统从文档中抽取的事实。

1. 一篇文档可以产生 0 条、1 条或多条事实。
2. 每条事实显示修改时间，可按修改时间升序或降序排序。
3. 律师可对事实执行：确认、取消确认、编辑、翻译、删除、恢复。
4. 如果事实有异议，点击「有异议」，填写异议意见后选择「重新解析」。
5. 系统会根据原事实、律师异议和可读取的来源文档文本重新生成事实，并把状态重置为待审核。
6. 对需要客户补充材料的事实，可提交补材料任务到任务中心。

建议把事实分为三类处理：

- 可直接使用：证据清楚，内容准确。
- 需要修改：基本正确，但表达、日期或名称需要调整。
- 暂不使用：缺少依据、重复或与当前案件无关。

事实确认前，不建议用于正式递交文案。

## 8. 知识库

知识库用于保存可复用内容，例如：

- EB-1A/NIW 论证框架。
- 推荐信结构。
- 律所常用表达。
- RFE 回复框架。
- 客户行业背景说明。
- USCIS 政策摘录。
- 文档解析提示词模板。

文档解析和文案生成弹窗都支持检索知识库内容。建议律所把常用模板整理成标准版本，减少不同成员之间的表达差异。

知识库内容应定期维护。过期政策、旧模板和不再使用的表达应及时删除或更新。

## 9. 生成和修改文案

进入「文案工作台」。

1. 选择要使用的事实和知识库材料。
2. 输入生成要求，选择策略后触发 Agent 生成文案。
3. Agent 会优先使用律师确认事实，也会参考选中的知识库材料、历史样例和策略说明。
4. 文案列表显示修改时间，可按修改时间排序。
5. 律师可对文案段落进行编辑、重写、翻译、导出和版本恢复。
6. 所有大模型输出会在后端清理 `<think>` 推理标签，再进入页面和数据库。

好的生成要求通常包含：

```text
任务目标 + 使用范围 + 风格要求 + 禁止事项
```

示例：

```text
请基于已确认事实，生成 NIW petition letter 中 proposed endeavor 部分。
只使用案件事实库中的内容，不要新增未提供的信息。
语气专业、正式，适合提交 USCIS。
如果证据不足，请用保守表达。
```

```text
请根据已确认事实，生成 EB-1A original contributions 部分。
重点突出客户专利被三家医院采用，并说明该采用如何体现领域影响。
不要编造引用、奖项或第三方评价。
```

AI 重写适合润色已有段落。常见指令：

```text
请让语气更正式，但不要增加新事实。
```

```text
请压缩到 300 字以内，保留所有关键事实。
```

```text
请改写为推荐信风格，突出推荐人的观察和评价。
```

重写后仍需律师复核，因为 AI 可能改变事实强度或增加不应出现的判断。

## 10. 翻译

翻译功能适合处理中英文材料、客户陈述和初稿内容。

建议用于初步翻译和内部理解。正式提交前仍应人工校对，重点检查：

- 法律术语。
- 人名、机构名和职称。
- 证书、奖项、专利和论文名称。
- 日期格式、金额、编号和地址。
- 否定句、条件句和责任归属。

如果翻译用于正式递交，应由律师或合格翻译人员最终确认。

## 11. 任务中心

「任务中心」用于管理待办、补材料请求、审核事项和 Agent 相关任务。

1. 律师可新建任务、修改任务状态、标记已完成、删除或恢复任务。
2. 任务显示修改时间，可按修改时间升序或降序排序。
3. 状态变更、完成、重开都会更新修改时间。
4. 全局任务页可跨案件查看待办；案件内任务页只展示当前案件任务。

建议每个任务写清楚：

- 负责人。
- 截止日期。
- 需要客户提供什么材料。
- 材料用途。
- 是否影响递交期限。

任务示例：

```text
请客户补充 2023 年获奖证书原件扫描件。
用途：用于 EB-1A awards criterion。
截止日期：2026-05-10。
```

## 12. 律师审核清单

任何 AI 辅助生成的正式内容，使用前至少检查：

- 是否有事实编造。
- 是否遗漏关键证据。
- 是否把弱事实写成强事实。
- 是否混淆不同客户或不同案件。
- 是否误解申请类别。
- 是否出现不存在的法规、案例或政策。
- 是否使用了未确认事实。
- 是否符合当前案件策略。
- 是否有过度承诺或夸大表达。
- 是否需要客户补充确认。

正式提交前还应检查：

- 客户姓名、出生日期、国籍、A-number、护照号等身份信息。
- 申请类别、表格名称、收件机构和提交目的。
- 所有关键事实是否可追溯到客户陈述或上传证据。
- 翻译内容是否忠实原文。
- 附件、证据编号和正文引用是否一致。

## 13. 常见问题

**文件解析成功，但大模型测试失败，为什么？**

文件解析可能使用 OCR、文本提取或本地解析逻辑，不一定依赖大模型。大模型测试失败通常只影响生成文案、AI 重写、翻译等模型调用。

**设置里显示有模型，但我没在网页保存过，为什么？**

可能是后端环境变量配置了模型。平台会显示实际生效配置，而不是只显示用户保存过的内容。

**修改 `.env` 后为什么页面没变化？**

如果使用 Docker，已运行容器不会自动读取新的 `.env`。需要重新创建后端和 worker 容器：

```bash
docker compose up -d --force-recreate --no-deps api worker
```

如果使用 Railway，修改 Variables 后，需要对 `api` 和 `worker` 执行 Redeploy。

**生成内容质量不好怎么办？**

优先检查三点：

- 上传材料是否完整。
- 事实是否经过确认。
- 提示词是否具体。

不要只写“帮我写一封申请信”。应明确申请类型、段落、事实范围和输出风格。

**能不能直接提交 AI 生成的文案？**

不建议。AI 生成内容必须经过律师审核、事实核验和格式调整后才能用于正式提交。

## 14. 内部使用建议

律所可以制定统一规则：

- 案件命名格式。
- 文件命名格式。
- 哪些材料必须上传。
- 哪些事实必须人工确认。
- 哪些文案必须由负责律师审核。
- 哪些知识库模板为标准版本。
- 谁可以修改模型设置。
- 谁可以删除文件、事实或知识库内容。

上线初期建议先选择 1-2 个案件试运行。确认文件解析、事实提取、文案生成、任务协作和模型稳定性都符合预期后，再扩大到更多案件。

## 15. 注意事项

- AI 输出只能作为律师草稿辅助，不能替代律师审查。
- 事实确认前不要直接用于最终递交文案。
- 客户联系方式应保持最新，便于补材料和案件沟通。
- 上传材料涉及隐私和商业秘密，建议仅部署在律所认可的服务器或私有环境中。
- 不要为了测试模型上传无关客户材料。
- 非律师人员不得未经律师审核直接向客户发送法律分析或申请策略。
