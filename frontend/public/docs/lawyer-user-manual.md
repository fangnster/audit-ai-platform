# 律师操作手册：当前实现版

更新时间：2026-04-27
适用对象：移民律师、案件助理、文案人员和律所内部管理员。
适用范围：当前系统已实现功能。本文按真实操作流程编写，不是远期规划。

本平台用于辅助移民案件材料整理、事实提取、翻译、知识库管理、任务跟进、文案生成和 AI 重写。AI Agent 可以提升整理和起草效率，但不能替代律师的事实核验、法律判断、申请策略和最终审核。

## 1. 使用原则

请把系统理解为“先整理证据，再沉淀事实，再生成草稿”的工作台。

核心原则：

- 先上传证据，再解析事实。
- 先审核事实，再生成文案。
- 只把确认过、可追溯的事实用于正式草稿。
- AI 输出只能作为初稿或辅助意见，正式递交前必须由律师审核。
- 线上使用大模型时，任务越小越稳定；不要一次性让 Agent 处理整个案件包或完整请愿书。

## 2. 5 分钟快速上手

第一次使用建议先用非紧急案件试运行：

1. 注册或登录账号。
2. 进入「设置」确认姓名、电话、公司/律所名称。
3. 进入「设置」中的模型设置，确认 Provider、Model、Base URL 和 API Key，并点击测试。
4. 进入「案件管理」新建一个测试案件。
5. 在案件详情页上传 1-2 份清晰材料。
6. 对文件点击「AI 解析」，选择合适文件类型并输入简短提示词。
7. 进入「事实库」，审核、编辑并确认可用事实。
8. 进入「文案生成」，只选择最相关事实，生成一个段落或一个章节。
9. 对草稿进行人工审核、AI 重写或翻译。
10. 在「案件任务」记录当前案件补材料和复核事项；跨案件待办在侧边栏「任务中心」查看。

## 3. 推荐案件流程

建议每个案件按下面顺序推进：

```text
创建案件
→ 上传文件
→ AI 解析文件
→ 审核事实
→ 确认可用事实
→ 补充知识库模板或策略
→ 分段生成文案
→ 律师审核和 AI 重写
→ 创建补材料任务
→ 更新事实和文案
→ 定稿
```

不要跳过事实审核直接生成正式文案。生成速度慢、质量不稳定、事实混淆，通常都和“事实未整理”“一次选太多材料”“提示词过泛”有关。

## 4. 账号、律所信息与设置

1. 登录使用邮箱和密码。
2. 注册时需要填写公司/律所名称。
3. 设置页可以修改姓名、电话、公司/律所名称。
4. 公司/律所名称当前只是用户资料字段，可展示、可编辑，不参与案件权限、知识库共享或业务筛选。
5. 设置页可切换明亮版和经典暗色版。
6. 设置页可配置告警总开关，并按类别分别控制是否弹出提示、是否写入历史。
7. 修改密码需要输入当前密码，新密码需二次确认。

系统管理员账号会在侧边栏看到「系统后台」。普通律师账号不会显示后台入口。

告警栏在页面顶部，用于轻量回看成功和失败提示。告警历史里的“名称”会尽量显示操作的源对象，例如原始文件名、事实内容摘要、文案标题、案件名、任务名或知识库标题，而不是只显示“已保存”“已删除”“解析完成”。如果只想减少弹窗干扰，可以在设置里关闭某类“弹出”，同时保留“历史”。

告警历史适合回答“刚才哪个文件解析失败了”“哪个文案生成完成了”这类问题；如果需要查看解析分块、覆盖率、事实依据和失败原因，请进入当前案件的「Agent 运行记录」。

## 5. 模型设置

进入「设置」中的模型设置，可以查看和保存大模型配置。

需要关注四个字段：

- Provider：供应商或网关，例如 `minimax`、`openai`、`claude`、`gemini`、`ollama` 或自定义 OpenAI-compatible 服务。
- Model：模型 ID，例如供应商要求填写的模型名称。
- Base URL：OpenAI-compatible `/v1` 地址。
- API Key：供应商密钥。

配置优先级：

```text
网页保存的模型设置 > 后端环境变量 > 程序默认值
```

API Key 不会明文回显。页面只会显示是否已保存或是否正在使用系统环境变量。

修改模型配置后，先保存，再点测试。线上如果修改服务器 `.env`，需要重启 API 和 Worker；只重启 API 会导致文案生成、重写等异步任务仍使用旧配置。

## 6. 案件管理

进入「案件管理」可以新建、搜索、排序、翻页和维护案件。

创建案件时填写：

- 案件标题。
- 案件类型。
- 客户姓名。
- 客户邮箱或客户电话，二者至少填写一个。
- 案件状态。

建议案件名使用统一格式：

```text
客户姓名 - EB-1A
客户姓名 - NIW
客户姓名 - I-485
客户姓名 - RFE Response
```

案件状态用于团队内部跟踪，例如接案、事实提取、文案起草、律师审核、已递交。案件删除后可进入回收站恢复；系统管理员有更高权限删除案件及相关对象。

## 7. 文件上传与文件类型

在案件详情页进入「文件管理」上传材料。

当前支持内置类型和用户自定义类型。常用内置类型包括：

- 证据材料。
- 获奖证明。
- 原创成果。
- 专利。
- 学术发表。
- 引用数据。
- 雇佣证明。
- 媒体报道。
- 专业组织。
- 推荐信。
- 申请信。
- RFI/RFE 回复。
- 其他。

文件类型可以在页面中自定义显示名称、图标和启用状态。自定义类型适合律所内部固定材料分类，例如“客户陈述”“专家评价”“商业采用证明”“行业报告”等。

上传建议：

- 优先上传可复制文本 PDF、Word 或清晰图片。
- 扫描件尽量先 OCR。
- 一个文件只放一种材料，避免把几十份证据打包成一个超大 PDF。
- 文件名保留客户、材料类型和日期，便于回溯。
- 上传后不会自动解析，需要律师手动点击「AI 解析」。

文件列表支持下载原始文件，也支持导出当前文档已提取事实组成的解析文案。

## 8. 知识库规则

知识库用于保存律师自己的常用内容。

当前实现的筛选规则非常重要：

- 只筛选当前律师名下的知识库。
- 不按组织或律所共享知识库。
- 所有入口只按知识库标题和标签检索。
- 不按知识库正文内容检索，避免把很长正文误带入 Agent。
- 文件解析和事实重解析只可选择「提示词模板」和「Agent 策略」。
- 文案生成和 AI 重写可以选择「提示词模板」「文案模板」「范文」「Agent 策略」。

建议知识库标题和标签写得非常清楚，因为检索只看标题和标签。

推荐标题示例：

```text
EB1A 原创贡献解析提示词
NIW proposed endeavor 生成策略
推荐信正式语气重写模板
RFE 证据不足保守表达策略
原创成果采用情况事实提取
```

推荐标签示例：

```text
EB1A, original contribution, parse
NIW, proposed endeavor, draft
RFE, conservative tone, rewrite
recommendation letter, formal style
```

## 9. AI 解析文件

文件上传后，点击「AI 解析」。解析弹窗支持输入律师提示词，也可以检索并选择知识库中的提示词模板或 Agent 策略。

解析适合做的事情：

- 从证据中提取可核验事实。
- 识别日期、机构、职务、奖项、专利、论文、采用方、引用数等。
- 提取对 EB-1A、NIW、RFE 等有用的事实。
- 把一份材料拆成多条可审核事实。

解析不适合做的事情：

- 要求 AI 判断案件是否一定能通过。
- 要求 AI 编造缺失证据。
- 一次解析几十份文件。
- 把完整申请策略和完整文案生成都塞进解析提示词。

好的解析提示词公式：

```text
申请类型 + 文件类型 + 要提取的事实重点 + 输出限制 + 禁止编造
```

示例：

```text
请从这份材料中提取可用于 EB-1A original contributions 的事实。
重点关注客户的原创贡献、第三方采用、可量化影响、专利/产品/技术名称和评价主体。
每条事实都要保留来源依据，不要补充文件中不存在的信息。
最多提取 8 条最强事实。
```

原创成果材料示例：

```text
请按原创成果角度解析这份材料。
优先提取：客户具体做了什么、该成果解决了什么问题、谁采用或评价了该成果、产生了什么可量化影响。
不要把普通岗位职责写成原创贡献。
```

推荐信示例：

```text
请从推荐信中提取推荐人亲自观察到的事实。
区分事实、评价和结论。
不要把推荐人的赞美性语言改写成不存在的客观证据。
```

线上避免卡住的解析技巧：

- 单个文件优先控制在合理页数内，超长 PDF 先拆分。
- 扫描件先做 OCR，减少模型猜测。
- 一次只解析一个文件，不要连续重复点击。
- 提示词要求“最多提取 5-10 条强事实”，不要要求“提取所有细节”。
- 大文件解析失败时，先拆为“证明页”“正文页”“附件页”分别解析。
- 解析时只选 0-2 条最相关知识库，避免 prompt 过长。
- 解析会在后台运行，提交后可以离开文件页；到当前案件的「Agent 运行记录」查看状态、提取事实数、文本质量、分块数、覆盖率、告警和失败原因。
- 如果同一文件已经在解析中，系统会阻止重复提交。长时间卡住的任务会被系统释放，释放后可以重新触发。

## 10. 事实库审核与异议重解析

进入「事实库」查看 AI 从文档中抽取的事实。

每条事实都可以：

- 确认或取消确认。
- 编辑。
- 翻译。
- 删除或恢复。
- 提出异议并重新解析。
- 创建补材料任务。

事实状态建议：

- 可直接使用：证据清楚、表达准确、来源明确。
- 需要修改：事实基本正确，但名称、日期、措辞或强度需要调整。
- 暂不使用：缺少依据、重复、与案件无关或风险较高。

点击「有异议」后，页面仍保持原有输入异议意见的风格。输入意见后再次点击重新解析时，系统会弹出与文件上传页解析一致的知识库选择弹窗。这里同样只可选择提示词模板和 Agent 策略。

异议意见建议写得具体：

```text
原事实把客户写成项目负责人，但文件中只显示客户是核心成员。
请重新提取时区分负责人、核心成员和参与者，不要夸大角色。
```

```text
这条事实遗漏了采用方名称和采用时间。
请从来源文档中补充采用机构、时间、应用场景和影响。
```

不要只写“有问题”“重新写”。异议越具体，重解析越稳定。

事实重解析会在后台运行。提交后可在当前案件的「Agent 运行记录」查看原事实、新事实、来源文件、异议长度、来源文本长度、知识库引用和失败原因。同一事实已有重解析任务时，系统会阻止重复提交。

## 11. 文案生成

进入「文案生成」生成或管理草稿。

生成前请确认三件事：

- 已选择正确案件。
- 事实库中已有足够确认事实。
- 知识库标题和标签能准确匹配当前任务。

文案生成适合按段落或章节进行，例如：

- EB-1A original contributions。
- EB-1A awards。
- EB-1A scholarly articles。
- NIW proposed endeavor。
- NIW national importance。
- RFE 回应中的某一项证据说明。
- 推荐信初稿。
- 客户陈述整理稿。

不建议一次性生成完整请愿书。线上远程模型请求时间长、失败率高，完整请愿书还容易让 AI 混淆事实。请按“一个 criterion / 一个章节 / 一个论点”分批生成。

好的生成要求公式：

```text
文案类型 + 具体章节 + 选择事实范围 + 论证重点 + 风格要求 + 禁止事项
```

示例：

```text
请基于已确认事实，生成 EB-1A petition letter 中 original contributions 部分。
重点突出客户的技术成果被三家医院采用，以及该采用如何体现领域影响。
只使用事实库和已选择知识库中的内容，不要新增未提供的信息。
语气专业、正式，适合提交 USCIS。
如果证据不足，请使用保守表达。
```

NIW 示例：

```text
请生成 NIW petition letter 的 proposed endeavor 部分。
围绕客户未来在人工智能医疗影像方向的工作计划展开。
请连接客户过往成果、未来计划和美国公共利益。
不要写成个人职业规划，也不要编造尚未提供的合作机构。
```

RFE 示例：

```text
请生成 RFE 回复中关于原创贡献证据不足的回应段落。
请先承认证据分类，再解释补充材料如何证明贡献、采用和影响。
语气克制，不要攻击审理意见。
```

线上避免卡住的生成技巧：

- 一次只生成一个章节或一个论点。
- 优先选择 6-15 条最相关确认事实。
- 知识库通常选择 1-4 条即可。
- 不要同时选择所有事实、所有范文和所有模板。
- Prompt 中明确“只生成本章节，不生成完整 petition letter”。
- 如果需要完整文案，先生成各章节，再人工整合。
- 点击生成后等待任务完成，不要短时间重复提交同一任务。
- 生成提交后可离开页面，在当前案件的「Agent 运行记录」查看排队、处理中、完成或失败。
- 同一案件已有文案生成任务排队或处理中时，系统会阻止再次发起，避免多个大模型任务互相抢资源。
- 长时间卡住的任务会自动释放，释放后可以重新触发。生成失败时先缩小事实数量和知识库数量，再重试。

## 12. AI 重写

AI 重写适合润色已有段落，不适合替代事实核验。

常见重写指令：

```text
请让语气更正式，但不要增加新事实。
```

```text
请压缩到 300 字以内，保留所有关键事实、日期和机构名称。
```

```text
请改写为推荐信风格，突出推荐人的亲身观察和评价。
```

```text
请降低确定性，把没有直接证据支持的表达改成保守措辞。
```

重写时可以选择知识库中的模板、范文或策略。仍然建议少量选择，优先选最贴近目标风格的一两条。

重写后必须检查：

- 是否新增了原文没有的事实。
- 是否改变了事实强度。
- 是否把推测写成确定结论。
- 是否误删日期、数字、机构名称和限定条件。

## 13. 翻译

翻译适合处理中英文材料、客户陈述、事实和文案段落。

线上翻译建议：

- 长文分段翻译。
- 一次翻译一个事实、一段陈述或一个章节。
- 对正式递交材料，翻译后人工校对。
- 对专利、论文、机构名、奖项名，必要时保留英文原文。

重点检查：

- 人名、机构名、职称。
- 证书、奖项、专利、论文名称。
- 日期、金额、编号、地址。
- 法律术语。
- 否定句、条件句和责任归属。

如果翻译请求很慢，先缩短文本，避免把完整证据包或完整请愿书一次性翻译。

## 14. 任务中心、案件任务与 Agent 运行记录

侧边栏「任务中心」用于查看跨案件待办。案件详情里的「案件任务」只看当前案件的处理待办、补材料请求和复核事项。

律师可执行：

- 新建任务。
- 修改任务状态。
- 标记完成或重开。
- 删除或恢复任务。
- 在案件内查看当前案件任务。
- 在全局任务页查看跨案件任务。

任务建议写清：

- 负责人。
- 截止日期。
- 客户需要补充什么材料。
- 该材料用于哪个申请类别或论证点。
- 是否影响递交期限。

示例：

```text
请客户补充 2023 年获奖证书原件扫描件。
用途：用于 EB-1A awards criterion。
截止日期：2026-05-10。
```

「Agent 运行记录」在每个案件内，位于「案件任务」后面。它不是普通待办，而是 AI 后台任务状态页。

当前分三类：

- 文件解析和重解析。
- 事实重解析。
- 文案生成和 AI 重写。

每条记录可以展开查看：

- 状态：排队、处理中、完成、失败或取消。
- 模型、创建时间、更新时间和耗时。
- 输入：文件名、事实名、文案标题、策略名、知识库标题、提示词长度等。
- 结果与诊断：提取事实数、事实分类、文本质量、覆盖率、告警、原事实/新事实、生成版本、错误原因等。

文案生成和 AI 重写中的事实依据会按普通换行展示，方便阅读，不再用醒目的特殊卡片。看到失败记录时，先根据错误原因缩小文件、事实或知识库范围，再重新发起。

告警历史和 Agent 运行记录的区别：

- 告警历史记录成功/失败提示，适合快速回忆最近操作，名称优先显示源文件、事实或文案标题。
- Agent 运行记录只显示当前案件的 AI 后台任务，适合追踪解析、重解析、生成和重写的详细输入、结果、诊断与错误。

## 15. 系统后台简要说明

如果账号拥有系统管理员权限，侧边栏会出现「系统后台」。

后台当前支持：

- 查看系统概览。
- 用户列表搜索、排序、分页。
- 案件列表搜索、排序、分页。
- 启用或停用用户。
- 授予或取消系统管理员角色。
- 重置用户密码，但不能查看原密码。
- 删除用户或案件，并处理相关业务对象。

系统管理员功能影响范围大，建议只给少数可信人员使用。删除用户或案件前应先确认是否已有数据库和文件备份。

## 16. Agent 大模型使用技巧

Agent 的稳定性主要取决于四件事：输入是否清楚、材料是否可读、任务是否足够小、模型服务是否稳定。

推荐做法：

- 用“章节任务”替代“全案任务”。
- 用“最强事实”替代“所有事实”。
- 用“少量模板”替代“全量知识库”。
- 用“具体禁止事项”约束 AI，例如不要编造、不要增加新事实、不要输出完整请愿书。
- 用“最多提取/生成多少条或多少字”控制输出长度。
- 对复杂文案先让 Agent 生成提纲，再生成单个章节。

不推荐做法：

- “帮我写一份完整申请信。”
- “把所有材料都分析一下。”
- “根据全部事实生成完整 petition letter。”
- “参考所有知识库内容。”
- “尽可能详细，不限制长度。”

推荐提示词模板：

```text
请完成一个有限任务：生成 [章节名称]。
只使用我选择的事实和知识库。
重点论证 [1-2 个核心点]。
不要增加未提供事实，不要编造引用、奖项、机构或法规。
如果证据不足，请使用保守表达。
输出控制在 [字数/段落数] 内。
```

解析提示词模板：

```text
请从当前文件中提取可核验事实。
申请类型是 [EB-1A/NIW/RFE]，关注 [criterion/主题]。
每条事实应包含主体、行为、时间、机构和证据依据。
最多提取 [5-10] 条强事实。
不要输出法律结论，不要补充文件外信息。
```

重写提示词模板：

```text
请重写下面段落，使其更适合 [petition letter/recommendation letter/RFE response]。
保留所有事实、日期、机构名称和限定条件。
不要增加新事实。
请让语气 [正式/克制/更有说服力/更简洁]。
```

## 17. 线上卡住或失败时怎么办

先判断是哪类问题：

- 页面一直转圈：可能是任务仍在队列、Worker 忙、模型响应慢或网络超时；先看当前案件的「Agent 运行记录」。
- 很快失败：通常是 API Key、Base URL、模型名、额度、速率限制或输入过长问题。
- 输出质量差：通常是事实未确认、提示词过泛或选择材料太多。
- 文件解析差：通常是扫描件质量、OCR 或文件过长问题。

律师端可先做的处理：

1. 不要连续重复点击同一生成或解析按钮。
2. 先打开告警历史确认最近成功/失败的是哪个文件、事实或文案。
3. 打开当前案件的「Agent 运行记录」查看任务状态和失败原因。
4. 缩小输入范围，只选最相关事实和知识库。
5. 把完整文案任务拆成单个章节。
6. 把大文件拆分后重新上传解析。
7. 到设置页测试模型配置。
8. 记录案件名、文件名、操作时间和错误提示，交给管理员查看 Worker 日志。

系统会自动释放超过保护时间仍未完成的 Agent 任务。释放后记录会显示失败和超时信息，解析或生成按钮也会恢复可点击状态。

管理员排查时重点看：

- API 是否正常。
- Worker 是否正常。
- Redis 是否正常。
- 模型 Provider 是否可访问。
- `agent_tasks.error_message` 是否有具体错误。
- 是否出现 429、timeout、invalid api key、context length 等模型错误。

## 18. 律师审核清单

任何 AI 辅助生成内容，使用前至少检查：

- 是否有事实编造。
- 是否遗漏关键证据。
- 是否把弱事实写成强事实。
- 是否混淆不同客户或不同案件。
- 是否误解申请类别。
- 是否出现不存在的法规、案例或政策。
- 是否使用了未确认事实。
- 是否符合当前案件策略。
- 是否有过度承诺或夸大表达。
- 是否需要客户补充确认。

正式提交前还应检查：

- 客户姓名、出生日期、国籍、A-number、护照号等身份信息。
- 申请类别、表格名称、收件机构和提交目的。
- 所有关键事实是否可追溯到客户陈述或上传证据。
- 翻译内容是否忠实原文。
- 附件、证据编号和正文引用是否一致。
- 请愿书各章节之间是否重复、矛盾或引用错证据。

## 19. 内部使用建议

律所可以统一下面规则：

- 案件命名格式。
- 文件命名格式。
- 文件类型和自定义类型命名。
- 哪些材料必须上传。
- 哪些事实必须人工确认。
- 哪些文案必须由负责律师审核。
- 哪些知识库模板为标准版本。
- 谁可以修改模型设置。
- 谁可以删除文件、事实、知识库、案件或用户。
- 线上卡住时由谁查看日志和联系模型供应商。

上线初期建议先选择 1-2 个案件试运行。确认文件解析、事实提取、文案生成、任务协作和模型稳定性都符合预期后，再扩大到更多案件。

## 20. 注意事项

- AI 输出只能作为律师草稿辅助，不能替代律师审查。
- 事实确认前不要直接用于最终递交文案。
- 客户联系方式应保持最新，便于补材料和案件沟通。
- 上传材料涉及隐私和商业秘密，建议仅部署在律所认可的服务器或私有环境中。
- 不要为了测试模型上传无关客户材料。
- 非律师人员不得未经律师审核直接向客户发送法律分析或申请策略。
